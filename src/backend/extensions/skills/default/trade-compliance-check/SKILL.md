# 外贸合规范围与证据核验

用于销售RFQ及商品运营的对外草稿。先阅读[工具契约](references/contract.md)；范围不足时使用[内部核验清单](references/review-checklist.md)提问。清单不是已核验法条，不能把完成提问称为通过合规检查。

## 执行顺序

1. 识别当前阶段：开发信、回复、Listing、合同、采购或出货。先读当前账号已保存的询盘或资料包，取得真实ID和revision；用途、型号和事实以来源为准。区分消费者Listing与B2B询盘，不把GPSR商品要约义务直接判给所有RFQ。
2. 确认目的地和平台。RFQ以询盘destination_country为准，英文不代表美国。Listing以用户确认的目标locale为准；Amazon US使用en_US。UK须区分GB/NI，美国州及欧盟具体成员国未知时保留，不自行猜测。儿童、医疗、食品接触、电气/无线用途未知时不能填“不适用”。
3. 真实调用trade_review action=knowledge，按channel检索当前规则，再按market_compliance查多国案例。需要背景时检索绑定的私有知识库，给出文件/章节来源。零匹配先清空query重试；没有相应规则应报告覆盖缺口，不能以英文常识替代已查询结果。
4. 读取localization-review技能后调用trade_review action=review。只传当前真实source_revision、明确channel及实际待审正文；不要传不存在的create/check/scoped动作或模型虚构的证书。询盘须已有当前报价，商品资料包须已确认事实且已生成。当前原生审核仅支持Alibaba RFQ和Amazon Listing；其他阶段输出待核验清单，明确没有执行对应阶段的程序审核。
5. 以真实回执展示市场/平台/商务条款及私有词库的风险、文字批注、依据和待确认事项。自动敏感词匹配沿用本机当前账号词库，生成后也会自动提示；不要装载另一套公开词库、另跑扫描脚本或用主观自查冒充系统结果。
6. 用户补充事实或请求改稿后，重新读取来源版本，组织新稿并再次review，传previous_review_id。展示已解决、持续和新增项以及来源/规则是否变化。任何source/证据/市场/产品版本变化都需复核；来源变化时不能沿用旧审核为“已通过”。
7. 用review/get真实回执展示原生审核卡与Markdown/JSON下载。基础资料包ZIP不自动被复审稿覆盖；最终平台改稿在审核报告draft中，分别展示两类下载，不重建假文件或拼接下载链接。

## 证据与时效

核对资料出具主体、产品/批次/版本、适用市场、声明范围、获取日期与文件明确有效期。文件没写有效期就标“未提供”，不能自设永久有效或猜测失效日期。证据内容冲突需保留双方来源，不选择性忽略。

当前来源指纹和规则版本用于判断输入是否变化，不能证明来源真实性、审核人身份或法规仍有效。能访问官方原文时再核对最新适用内容；不能访问则说明使用项目核验快照及其日期。网站链接存在不等于已经查询。模型不得自行创建“财务已审核”“认证已通过”等事实。

## 结果边界

交付：已检查范围、发现的问题、缺少的证明、可执行修改和需要人工/专业确认的事项。普通PP收纳盒不因出口欧盟就自动要求CE；B2B准备提醒不等于认定违法。未命中不等于完整法律合规，人工确认也不是发布许可。本技能不发信、签署、支付、替人验收或发布商品。
